# What the integrator changes for reviewer v1.1 (on top of `INTEGRATION.md`)

Nothing here is built; these are the pipeline owner's files (`reviews/ai/`, `src/`, `drizzle/`, `chain-fixes/`). The semantics to implement are `review_rules_v1_1.py` (`outcome`, `ACTION_CLASS`, `needs_second_pass`, `effective_decision`) and `README-v1_1.md` §2; import or mirror them. `INTEGRATION.md` §1-5 stand except where this file replaces them.

| # | where | change | why |
|---|---|---|---|
| 1 | specialist registry (`procedures.ts`, `specialists.json`) | register `chain-reviewer` version **1.1.0**, prompt `reviewer/prompt-reviewer-v1_1.md`, sha256 `1136aec2c975aebd0f4b8f17cf14d6ad1410229c33b97e7d8382b8258cb735f6` (v1.0.0's hash `46606e81…` is the pilot's only) | a run is reproducible by prompt hash |
| 2 | `chain-review-record.ts` (new, `INTEGRATION.md` §2) | record per ITEM: call `validate_review_v1_1.validate_output(output, packet)`; write one review row per valid item; an invalid item becomes a row `review_invalid` with its reason and stays exactly as it was; never drop a packet for one bad item. Take opaque-to-fix ids from `<set>/private/id_map.json`, or ingest `private/outcomes.tsv` (`record_reviews_v1_1.py` writes it) | the pilot lost 9 right reviews to one invalid item |
| 3 | `chain-fix-decide.ts`, `reconcile` | the transitions of `INTEGRATION.md` §3 are replaced by `review_rules_v1_1.outcome` (table in `README-v1_1.md` §2). New facts it needs: `status` (`held` / `pending` / `applied`, from the fix's CURRENT state), `codes` (the fix's holds), `readers_agree`, `agreed_empty`, `second_run_agrees` (pass 2 and pass 1 corrected routes equal under `readings_agree_v3_4`; `record_reviews_v1_1.second_run_agrees` is the reference), `stored_equals_reading`, `correction_is`, `human` | one rule, one place |
| 4 | the fix state machine | **an applied fix is never reverted by a correction or a referral**: state `accepted` + `ai_disputed: {run_id, correction?}` (new flag, database stays `applied`), the correction queued for pass 2; pass 2 with the same routes supersedes the reading with a NEW fix (`ai_corrected: {runs: [...]}`) and applies it in place; a revert happens only for `keep_stored` when the stored chain differs, or on a human's word | owner amendment (b), (d); the pilot showed reverting gains nothing (80cd84, d695ec: stored chain equals the reading) and harms (e87ace) |
| 5 | `stored_equals_reading` | compute it from the fix's own `comparison` (`routes_before`, `routes_after`, `added`, `removed`, `changed` empty) rather than the reviewer's approximation (`review_rules_v1_1.stored_equals_reading`: link-key equality of stored branches and reader A's routes, derived links aside) | the pipeline has the real comparison |
| 6 | `correction_is` | keep the inherited-names check: the tool's `readings_agree` ignores `inherited` links, so a correction that changes only whom a report inherits would count as a confirmation | cr1-6dfc38 |
| 7 | the hold table | add `withheld_by_earlier_check` (clearable) only if the pipeline wants to carry it; the reviewer sees it as a hold on tranche readings that were tool-eligible but kept off the apply lists (`withheld_by_judge.txt`: t01 3, t02 5) | the reviewer reviews them on the Arabic |
| 8 | review row | `question` may be set on any decision (a note naming an unruled question; ruling 11 included); `corrected_reading` may accompany `refer_to_human` (never applied without a human); store both | prompt 1.1.0 |
| 9 | labels (`chain-structure.ts`, `public_chain_fix_labels`) | add the disputed label: "Read by model; disputed by AI review (claude-opus-5-5), <date>; awaiting second review". The other three labels of `INTEGRATION.md` §4 stand. Never "verified" | owner amendment (b) |
| 10 | `pending` | a tranche reading cleared by v3.3 and not yet applied is `pending`: review it before or after applying; the outcome follows the real state at recording time, not the packet's `status` | sets B eligible are built `pending` |
| 11 | `/method`, `model_registry.json`, `RUNBOOK.md` | the paragraph and entry of `INTEGRATION.md` §5 gain: per-item recording; an applied reading is labelled disputed, not reverted; a correction equal to the reading is a confirmation; the pilot re-score (`README-v1_1.md` §4) with its limits | published method |
| 12 | reader toolchain | `FORMAT_GAP.md` (out-of-order connecting chain): a v3.5 reader layer, prompt rule and consumer audit | the class the format cannot hold |

Outcomes the pipeline reads from `private/outcomes.tsv` (columns `opaque, id, status, holds, not_clearable, valid, decision, effective, outcome, action_class, second_pass, second_run, uncertainty, question, problem`); `RUN.md` §4 maps each outcome to an action and a label.
Order of work for a first run: items 1, 2, 3, 4 and 9 are needed before any `apply_*` or `label_*` outcome is acted on; a first run can stop at the record step (nothing applied) and be read by a person.
