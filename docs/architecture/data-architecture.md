## 1. Decision

| Concern | Choice |
| --- | --- |
| Store | Railway's official PostgreSQL template, image `ghcr.io/railwayapp-templates/postgres-ssl:18`, one small always-on instance tuned for low memory |
| Access layer | Drizzle ORM `drizzle-orm` 0.45.4 with `drizzle-kit` 0.31.11 (the stable pair, not the 1.0 release candidate), driver `postgres` (postgres.js) |
| Where SQL lives | `src/db/queries/` for the app, `src/db/load/` for the loader, `drizzle/` for migrations. Never in server actions, pages or components |
| Migrations | Generated by `drizzle-kit`, checked in under `drizzle/`, applied by a Railway pre-deploy command |
| Vector search | `pgvector` (0.8.x ships in the template image), in its own table, created by an ordinary core migration when the first embedding writer ships (step 11). No approximate index at launch |
| Text search | Arabic: trigram index on text normalized by the project's own Arabic `norm()`. English: a `tsvector` full-text index. Names and titles: trigram |
| Graph questions | Fixed-depth joins, one self-join for chain adjacency, one materialized view for teacher and student links |
| Graph analytics | Offline in Python over an export of the teacher and student view; results are not stored until a feature needs them |
| Bulk load | The Python bundle is projected to plain CSV and loaded with `COPY ... FROM STDIN` into staging tables, then merged by stable ID |

### 1.1 Why not Neo4j

The application never uses a graph feature. Its query sites contain no
variable-length path, `shortestPath`, APOC, GDS, full-text index or vector
index. Every query is a fixed-depth join such as Hadith to Chain to Narrator.
Neo4j averaged 1.78 GB of memory, which is about $18 a month of RAM alone at
Railway's $10 per GB-month, and its wake-from-sleep window causes HTTP 500s.

### 1.2 Why Railway Postgres, judged against the alternatives

Railway prices, from `docs.railway.com/pricing/plans`: RAM $10 per GB-month,
CPU $20 per vCPU-month, egress $0.05 per GB, volumes $0.15 per GB-month. The
Hobby plan costs $5 a month and includes $5 of usage, so a bill under $5 of
usage costs exactly $5.

| Option | Estimated memory | Estimated bill per month on Hobby | Verdict |
| --- | --- | --- | --- |
| **A. Railway Postgres template, tuned, always on** | app 150 to 250 MB, database about 250 to 450 MB billed until measured (section 1.4) | **$5 to $8** | **Chosen** |
| B. SQLite file on a volume inside the app service | app 250 to 350 MB including page cache | $5 | Saves $1 to $2 only, at real cost: single writer, downtime on every redeploy, no migrations in pre-deploy, volume permission problems with the non-root image, and `sqlite-vec` is pre-1.0 |
| C. Turso (hosted libSQL) | app only | $5 to $10 | Every query crosses the public internet. A brute-force vector query reads 99k rows, so the free 500M rows-read allowance runs out after about 5,000 searches |
| D. Neon | app only | about $20 | Free tier's 1 GB is too small once vectors are added |
| D'. Supabase | app only | about $30 | Pro plan floor is $25 |
| Status quo, Neo4j | 1,780 MB | about $20 or more | Sleeps and returns 500s |

Postgres wins on the owner's first priority, low memory, by removing about
1.6 GB of RAM, and costs about the Hobby floor. SQLite is lower still, but only
by $1 to $2 a month, and it trades away multi-writer curation and zero-downtime
deploys, both of which this product needs because curators write through the
app.

The template image already contains `pgvector` 0.8.x, `pgaudit` and
`pg_stat_statements`, according to its Dockerfile and README. Railway's
documentation page still says the templates ship no extensions. The image
source is treated as authoritative, but the first provisioning step checks
`select * from pg_available_extensions where name = 'vector'` (section 12,
step 8). The vector migration fails closed if the extension is missing.

### 1.3 What would flip this decision

| Condition | Flip to |
| --- | --- |
| Curation becomes single-writer admin-only, a few seconds of downtime per deploy is acceptable, and the whole system must fit under about 250 MB | SQLite on a volume |
| The app leaves Railway's container model for edge or serverless hosting, and per-page query counts are batched down | Turso |
| Per-pull-request database branches become a priority | Neon |
| Semantic search must run filtered approximate search over 1,024-dimension vectors at low latency and the bit pre-filter (section 7.4) misses too much | A larger Railway Postgres with an HNSW index, about 300 to 400 MB more RAM, roughly $3 to $4 a month more |

### 1.4 Memory budget

The Postgres figure is derived as a worst case, not guessed. Research puts
the per-process floor at about 60 to 100 MB on top of `shared_buffers`, cites
333 MB billed after one large index scan, and a reported idle floor near
300 MB (finding 05).

| Term | Value with section 2.4 settings |
| --- | --- |
| `shared_buffers` | 64 MB |
| Server process floor (postmaster, checkpointer, walwriter, stats) | about 60 to 100 MB |
| Autovacuum: `autovacuum_max_workers` x `autovacuum_work_mem` | 2 x 32 MB = 64 MB at most |
| App pool: 5 backends x (backend RSS about 10 MB + `work_mem` 4 MB x `hash_mem_multiplier` 2 x about 2 hash or sort nodes) | about 130 MB at most, about 50 MB typical |
| Loader session (only during a load window, `max: 2`) | about 40 MB plus its `maintenance_work_mem` 64 MB |
| Hot index set: GIN trigram on Arabic (unmeasured), name trigram indexes, chain and hadith btrees | about 50 to 150 MB of page cache |
| **Total, steady state** | **about 250 to 450 MB** until measured |

| Process | Expected billed memory |
| --- | --- |
| Next.js standalone server | 150 to 250 MB |
| Postgres, tuned as in section 2.4 | about 250 to 450 MB, derived above |
| Vector search, if 1,024 dimensions with the bit pre-filter | about 20 MB more hot set, with filter columns on the vector table (section 7.4) |
| Vector search, if 384 dimensions with exact scan | about 81 MB more hot set |
| Neo4j today, for comparison | 1,780 MB average |

These are estimates. Railway bills Linux page cache as container memory
(community reports, not documentation), so the database figure depends on how
much of the data is read. The bill estimate carries the research's range of $5
to $8 a month. The first deploy measures it (section 12, step 8), and the
estimate is replaced by the measurement.

### 2.3 Connection budget

`max_connections = 20` is set on the server. The app pool holds at most 5.
During a deploy the old and new app instances overlap, so 10 can be in use,
plus 1 for the pre-deploy migrator, up to 2 for a loader and a couple of
`psql` sessions: 15. The 3 slots Postgres reserves for superusers are real
headroom only because the app, migrator and loader are not superusers
(section 2.9).

### 2.4 Postgres memory settings

Applied once with `ALTER SYSTEM`, which writes `postgresql.auto.conf` on the
volume. The image's wrapper also writes that file: when it holds no
`max_connections`, the wrapper appends `max_connections = 500`, and it edits
`shared_preload_libraries` there when an operator sets it
(`postgres-ssl_wrapper.sh` lines 428 to 457). Until the tuning is applied, and
on any fresh volume, the server therefore runs with 500 connections and the
default 128 MB of shared buffers. The settings are kept in
`src/db/ops/railway-tuning.sql` and applied by hand with `psql` as the
superuser, then the service is restarted. This is a gated checklist item in
step 8, before any load, and `db:verify` checks `show max_connections` is 20
and `show shared_buffers` is 64MB. They are not a migration, because `ALTER
SYSTEM` cannot run inside a transaction.

```sql
alter system set shared_buffers = '64MB';               -- restart required
alter system set max_connections = 20;                  -- restart required
alter system set work_mem = '4MB';
alter system set maintenance_work_mem = '64MB';         -- raised per session only by src/db/ops/indexes-heavy.sql
alter system set autovacuum_work_mem = '32MB';          -- explicit; -1 would let each worker take maintenance_work_mem
alter system set effective_cache_size = '256MB';        -- planner hint, allocates nothing
alter system set max_parallel_workers_per_gather = 1;   -- parallel workers use /dev/shm, 64 MB by default
alter system set autovacuum_max_workers = 2;            -- restart required
alter system set max_wal_size = '512MB';                -- bounds WAL on the 5 GB volume during a load
alter system set jit = off;
alter system set huge_pages = off;
```

Per-role settings (`statement_timeout`, `idle_in_transaction_session_timeout`,
`work_mem`) live in `src/db/ops/roles.sql` (section 2.9).

Do not `ALTER SYSTEM SET shared_preload_libraries`; the image's wrapper owns
that list. These values are engineering judgement, not benchmarks.

### 2.5 Backups

- Railway scheduled volume backups: daily, weekly and monthly, all enabled.
  They are incremental and billed at the volume rate on the bytes they hold
  exclusively. They expire automatically (daily after 6 days, weekly after
  27), can be restored only into the same project and environment, and manual
  backups are limited to half the volume size. They are therefore not the
  archive of curation work.
- No point-in-time recovery. Its WAL archiving has been reported to inflate
  billed memory.
- **Off-platform curation archive.** A weekly operator task,
  `npm run db:backup-curation`, dumps the curation and operations tables
  (section 4.1) with `pg_dump --format=custom` into `.omc/backups/postgres/`
  and copies the file to the owner's off-machine store (assumption: a cloud
  drive the owner names, section 14 question 12). The loader also takes this
  dump before every bulk load. Backups are never deleted by tooling.
- `pg_dump` must be at least the server's major version. Production is
  Postgres 18 and this machine has only 16 and 17 client tools, so every dump
  runs inside a pinned `pgvector/pgvector:pg18` podman container. The loader
  and the backup task assert `pg_dump --version` major is at least
  `server_version_num / 10000` before starting.
- Pipeline tables are rebuilt from the bundle, not restored. The bundle and
  its 37-column input are gitignored and exist on one developer machine, so
  the owner must keep an off-machine copy of `datasets/hadith-data/development/`
  and the bundle directory (section 14 question 12).

### 2.5.1 Restore

| Scenario | Procedure |
| --- | --- |
| Bad load or bad migration within 6 days | Railway restore of the volume backup into the same environment, then redeploy the app |
| Volume lost, or backup expired | Provision a fresh Postgres, apply `roles.sql` and the tuning, run the migrator, `db:load` the current bundle, then `pg_restore --data-only` the latest curation archive into the curation and operations tables, then `db:verify` |

Targets: recovery point one week for curation (the weekly archive), recovery
time about two hours. Both procedures are rehearsed once in step 8 against a
throwaway Railway environment before the first production load.

### 2.6 Migrate on deploy

`railway.json` at the repository root (field names must be checked against
Railway's current schema before committing):

```json
{
  "$schema": "https://railway.com/railway.schema.json",
  "build": { "builder": "DOCKERFILE", "dockerfilePath": "Dockerfile" },
  "deploy": {
    "preDeployCommand": ["node", "migrate.mjs"],
    "healthcheckPath": "/api/health",
    "healthcheckTimeout": 60,
    "restartPolicyType": "ON_FAILURE",
    "restartPolicyMaxRetries": 5
  }
}
```

- The pre-deploy command runs in the built image, on the private network, with
  the app's variables. A non-zero exit blocks the release.
- The Next.js standalone output only contains files the app imports, so it
  will not contain the migrations or the migrator. The Dockerfile's builder
  stage bundles `src/db/migrate.ts` into one file `migrate.mjs` with esbuild,
  and the runner stage copies `migrate.mjs` and the `drizzle/` folder.
  `drizzle-kit` is a development dependency and never ships in the image.
- `migrate.ts` applies the single `drizzle/core` stream as `schema_owner`.
  There is no conditional stream: the vector table arrives as an ordinary
  migration in step 11, and that migration fails if `pgvector` is missing.
- **Migration rules.**
  - Expand only. A release may add tables, columns, indexes and views. A
    rename or drop ships one release later, after no deployed code reads the
    old shape, because the old app instance keeps serving while the
    pre-deploy command runs.
  - `migrate.ts` first runs `set lock_timeout = '5s'` and `set
    statement_timeout = '60s'`, then takes the same `pg_advisory_lock` key as
    the loader, so a migration and a load never run together. It retries a
    lock timeout three times with backoff, then exits non-zero.
  - Large index builds (the Arabic GIN trigram index, any future vector
    index) are not migrations. They live in the checked-in
    `src/db/ops/indexes-heavy.sql`, use `create index concurrently` (which
    cannot run inside a transaction block, and the drizzle migrator wraps
    migrations in one; assumption to verify against drizzle-orm 0.45.4), set
    `maintenance_work_mem` for that session only, and are run by an operator
    in a load window.
  - The Railway Pre-deploy Timeout is set to 300 seconds in the service
    settings in step 8. The default is no limit, so a migration waiting on a
    lock would otherwise hold the deployment indefinitely.
- `/api/health` runs `select 1` with a two-second timeout, so a database that
  cannot be reached fails the health check at deploy time. Railway does not
  re-check health after a deploy is live, so an external uptime probe (any
  free monitor, every 5 minutes) watches `/api/health` from step 8. It is the
  measurement behind "no 500s on idle".
- **When the database is unavailable.** Railway documents downtime on every
  redeploy of a service with a volume, even with a health check: tuning
  restarts, image updates and the certificate renewal redeploy. Read queries
  retry connection errors (`ECONNREFUSED`, SQLSTATE `57P01` and `57P03`) twice
  with 250 ms and 1 s backoff inside `src/db/queries`. Writes do not retry.
  `src/app/error.tsx` says the service is temporarily unavailable and offers a
  retry. Database restarts happen only in announced maintenance windows.
- Every page that reads the database declares `export const dynamic =
  'force-dynamic'`, and the client connects lazily on first query, so
  `next build` never needs a database.
- `tsconfig.json` must exclude `src/scripts` (operator scripts get their own
  `tsconfig.scripts.json`). Today `next build` type-checks every operator
  script, which is a likely cause of the failed image build of 2026-08-18
  (unconfirmed: Railway returned no diagnosis).

### 2.8 Disk budget

Research estimates the database at 1 to 2 GB on disk; it is measured after
the first local load.

| Item | Estimate |
| --- | --- |
| Live tables and their indexes (pipeline and curation) | 1 to 2 GB |
| Staging peak during a load (`UNLOGGED load_<table>` copies of every pipeline CSV) | about 0.6 GB |
| Dead tuples left by a load (only changed rows are rewritten, section 4.3) | small; `VACUUM (ANALYZE)` runs after commit |
| WAL | bounded by `max_wal_size = 512MB` |
| Vectors at step 11 | `halfvec(1024)` about 271 MB plus `bit(1024)` about 18 MB |
| Headroom | at least 50 percent free, because manual backups are limited to half the volume |

The loader compares `pg_database_size` with the volume size before `COPY`
and refuses above 50 percent. If the measured local size exceeds about 1.5 GB,
grow the volume before the first production load; at 100 percent Railway
resizes offline and restarts the service.

### 2.9 Database roles

`src/db/ops/roles.sql` is applied once by an operator as the template
superuser, before the first migration.

| Role | Rights | Used by |
| --- | --- | --- |
| `schema_owner` | Owns the schema and every object; no `SUPERUSER`, no `CREATEROLE` | The pre-deploy migrator, the loader, `indexes-heavy.sql` |
| `app_rw` | `SELECT` on everything; `INSERT` and `UPDATE` on curation and operations tables only; no `DELETE` anywhere (curation uses `retired_at`); `EXECUTE` on `apply_decision` and `refresh_network` | The app. Settings: `statement_timeout = '3s'`, `idle_in_transaction_session_timeout = '10s'`, `work_mem = '4MB'` |
| Template superuser | Everything | An operator only: `roles.sql`, tuning, emergencies |

With no superuser client, an injection or a mistake in a raw `sql` template
cannot run `COPY ... TO PROGRAM`, and the public views are the read boundary
for public pages by code review and lint rule (section 3.2), not by grants:
the app role must also read base tables for reviewer mode.

### 3.2 Rules

1. **Server actions contain no SQL.** Files under `src/app/**` may not import
   `drizzle-orm`, `postgres`, `@/db/client` or `@/db/schema`. Enforce with an
   ESLint `no-restricted-imports` rule scoped to `src/app/**`. Actions validate
   input with zod (a new dependency), call one query function and return its
   result.
2. **Server components read through query functions directly.** A read that
   only a server component needs is not a server action at all, so it is not
   exposed as a public POST endpoint. Reads that a client component calls go in
   `src/app/actions/read/`.
3. **One row mapper per entity** in `src/db/queries/mappers.ts`. It reproduces
   the snake_case keys and the aliases the UI reads today where a source
   column exists (`title`, `primary_topic`, `text_english`, `text_arabic`,
   `birth_year_hijri`, `year_hijri`, the synthesized variation with `source:
   'hadith_node'`), casts counts to numbers and turns timestamps into ISO
   strings. Every list and detail query uses it, which fixes the blank titles
   in the unfiltered admin hadith list. Fields with no source column
   (`display_grade`, `auto_calculated_grade`, `transmission_type`,
   `reliability`, `biographical_narrative`, the per-date provenance fields)
   are **not** reproduced; section 9.4 defines their replacement contracts and
   names the UI files that change with the port.
4. **Writes take an actor.** Every write function in `src/db/queries/` takes
   `actor: string` and writes its `curation_audit` row inside the same
   transaction (section 10).
5. **Updates use explicit column allowlists.** Partial updates build the `set`
   object from an allowlist and convert `undefined` to `null` only for keys the
   caller sent. Drizzle's `.set()` ignores `undefined`, whereas the Neo4j
   driver turned it into `null`, so `updateHistoricalEvent` would otherwise stop
   clearing fields.
6. **Every read filters `retired_at is null`** on every table that has the
   column, pipeline and curation alike, including link tables. Today no
   action filters tombstoned rows. Only reviewer-mode history views and
   `db:verify` read retired rows. Unique constraints on curation tables are
   partial (`where retired_at is null`), so a retired tag or tradition can be
   re-created; `on conflict` targets name the same partial index.
7. **Never `||` for nullable numbers.** Use `??`. `createLocation` turns a
   latitude of 0 into null today.
8. **Enum values never come from raw input.** Every value compared with or
   written to an enum column is first mapped to a canonical value in
   TypeScript (zod transform). Legacy aliases (`Shia`, `Shia Imami`,
   `Political`) are resolved there; an unknown value gives an empty result for
   a filter and a validation error for a write, never a Postgres cast error.
9. **Public pages read public views.** Any query that serves an anonymous
   page reads `public_*` views (section 11.3), never base `hadiths` or
   `translations`. Base tables are read only by curator and reviewer-mode
   queries, which live in files named `*-review.ts` so the rule can be checked
   by lint.
10. **Reads retry, writes do not.** Read query functions are wrapped in
    `withReadRetry` (section 2.6). Curation writes set `lock_timeout = '3s'`
    and refuse with "data load in progress, try again later" while a
    `dataset_versions` row has `load_status = 'loading'`.

### 3.3 Connection handling for a Next.js standalone server

`src/db/client.ts`:

- Starts with `import 'server-only'` (add the `server-only` package).
- Creates one postgres.js client per process, cached on `globalThis` so
  development hot reload does not multiply pools.
- Creates it lazily on first use, never at import time, so builds do not
  connect.
- Options: `max: 5`, `idle_timeout: 20` (seconds), `connect_timeout: 5`,
  `ssl: false` when the host ends in `.railway.internal`, `ssl: 'require'`
  otherwise. No `prepare: false` (there is no transaction-mode pooler).
- On `SIGTERM` it calls `sql.end({ timeout: 5 })` so draining deploys close
  connections cleanly.
- Exports `db = drizzle(client, { schema })`.

The migrator and the loader create their own short-lived clients (`max: 1`
and `max: 2`) and close them on exit.

## 4. Ownership, identifiers and reloads

### 4.1 Table ownership

Every table has exactly one owner class, and every column has exactly one
writer path. This is the rule that lets a data reload run without destroying
curation work. The one deliberate exception, derived columns on pipeline
tables, is named below with its two writers.

| Owner | Written by | On reload |
| --- | --- | --- |
| **Pipeline** | The bulk loader only, from the validated Python bundle | Upserted by stable ID. Rows absent from the new bundle get `retired_at`; nothing is deleted |
| **Candidate** | The bulk loader only, from the projection's separate, manifest-bound candidate stream (section 4.4) | Replaced per load. Never read by public, search or research queries; reviewer mode only |
| **Curation** | The app through curator server actions, plus one-time seeds and the one-time Neo4j export, each recorded with a `system:` actor | Untouched |
| **Derived** | The loader, and two `security definer` SQL functions the app may call: `apply_decision(unit_id)` and `refresh_network()` | Rebuilt from pipeline and curation rows |
| **Operations** | The loader, operator scripts and the app's audit writer | Append-only, except `dataset_versions` status fields |

| Pipeline | Candidate | Curation | Derived | Operations |
| --- | --- | --- | --- | --- |
| `traditions`, `sources`, `collections`, `books`, `chapters`, `hadiths`, `translations`, `narrators`, `narrator_lexicon_profiles`, `narrator_aliases`, `narrator_teachers`, `chains`, `chain_mentions`, `hadith_assessments`, `bibliographic_works`, `editions`, `citations`, `biographical_assertions`, `temporal_assertions` | `translation_candidates`, `resolution_review_units` | `collection_rights`, `narrator_surface_decisions`, `chain_absence_dispositions`, `narrator_bios`, `narrator_same_as`, `narrator_assessments`, `locations`, `historical_events`, `epochs`, `narrator_events`, `narrator_locations`, `commentaries`, `commentary_hadiths`, `commentary_narrators`, `religious_traditions`, `schools_of_thought`, `source_texts`, `cross_parallels`, `motif_tags`, `hadith_motif_tags`, `parallel_motif_tags`, `narrator_religious_traditions`, `location_religious_traditions` | `narrator_transmissions` (materialized view), `hadith_embeddings`, and the derived columns listed below | `dataset_versions`, `curation_audit`, `parallel_research_runs` |

**Derived columns on pipeline tables.** These are written by the loader and
by `apply_decision(unit_id)`, and by nothing else:

- `chain_mentions.narrator_id`, `resolution`, `link_kind`, `decision_id` when
  the value comes from a human decision (the loader writes the automatic
  values; replay and `apply_decision` overlay decisions);
- `hadiths.source_text_status`, `chain_status`, `grading_status`;
- `chains.verified_link_count`.

`apply_decision(unit_id)` runs inside the curator's decision transaction. It
re-applies the live decision for that unit to its mentions, recomputes the
facets of the affected hadiths and chains with `is distinct from` guards, and
returns the number of rows changed. A decision is visible on the chain page
as soon as the transaction commits. `narrator_transmissions` is not refreshed
per decision: it is refreshed by the loader and by the curator action
`refreshNetwork`, which calls `refresh_network()`; that function takes an
advisory lock (one refresh at a time, skipped if one is running), sets
`work_mem = '32MB'` for its own transaction only, and runs `refresh
materialized view concurrently`. The network page shows the refresh time.

Two clarifications:

- The evidence tables are pipeline-owned because citation curation already
  happens in reviewed files in the Python pipeline
  (`datasets/hadith-data/evidence_curation.json`). A curator cannot create a
  citation in the app; publishing a verdict that needs a new citation is a
  round trip through that file and a reload. This is deliberate: citations
  are reviewed with the same gates as the rest of the evidence bundle.
- `collections` is pipeline-owned and carries no rights. The owner's rights
  decision lives in the curation table `collection_rights`, so a reload can
  never overwrite it.

### 4.2 Identifiers

All primary keys are `text`, except identity columns on link tables and
`curation_audit`. Pipeline keys are the namespaced IDs the bundle contract
already produces. Report, narrator and work keys derive from immutable
upstream keys and are the same on every rebuild. Chain and mention keys are
positional outputs of the extractor: a change to taḥwīl stitching, the
branch-limit retry (64 to 256) or empty-branch dropping can renumber them. The
loader therefore records the extractor version and hash on
`dataset_versions`, reports every mention whose ID is unchanged but whose
`surface_normalized` changed, and never replays a decision onto such a
mention (replay matches on the unit key, which hashes the surface, so the
decision becomes an orphan and is re-queued, section 4.3).

| Entity | Primary key format | Natural key |
| --- | --- | --- |
| Dataset version | the projection's content SHA-256 (64 hex) | same |
| Tradition | `tradition:sunni`, `tradition:imami`, `tradition:zaydi`, `tradition:ibadi` | `code` |
| Source (upstream provider) | `source:<slug>` | `slug` |
| Collection (source work) | `collection:<source_work_id>` | `source_work_id` |
| Book, chapter | `book:` or `chapter:` plus a 24-hex stable hash of their parts | the hashed parts |
| Hadith | `hadith:<record_id>` | `record_id` (namespaced `k6:`, `pure-canon:`, `thaqalayn:`, `openiti:`) |
| Translation (source) | The bundle's own `translation:<record_id>:en` | (`hadith_id`, `language`) |
| Translation candidate | `translation-candidate:<record_id>:<language>:<candidate source>` | (`hadith_id`, `language`, `candidate_source`) |
| Narrator, rawi lexicon | `narrator:rawi:<scholar_indx>` | (`authority`, `authority_key`) |
| Narrator, future Imami authority | `narrator:imami:<work>:<entry>` | (`authority`, `authority_key`) |
| Chain | `chain:<record_id>:<branch, 4 digits>` | (`hadith_id`, `branch`) |
| Chain mention | `mention:<record_id>:<branch, 4 digits>:<position, 4 digits>` | (`chain_id`, `position`) |
| Hadith assessment | `assessment:<record_id>:<tradition code>:<source_field>:<ordinal, 2 digits>` | (`hadith_id`, `tradition_id`, `source_field`, `ordinal`) |
| Review unit, coarse | SHA-256 of `surface_normalized`, `teacher_context_normalized`, `source_work_id` | same |
| Review unit, fine | SHA-256 of `surface_normalized`, `teacher_context_normalized`, `student_context_normalized`, `source_work_id` | same |
| Seeded event or location | the existing stable seed ID, for example `historical-event:<24 hex>` | same |
| Other curation rows | `gen_random_uuid()::text`, or the existing Neo4j UUID for migrated rows so links in the wild keep working | `id` |

Two consequences:

- Every Neo4j `id` UUID on pipeline nodes was random per load and is dropped.
  Curated rows that pointed at those UUIDs (commentaries, parallels, the
  parallel `pipeline_key`) are re-keyed to `hadith:<record_id>` and
  `narrator:rawi:<scholar_indx>` during the one-time export.
- The bundle's numeric `id` column is display order only and is not loaded.

### 4.3 Reload strategy

A reload is one operator command, `npm run db:load -- --bundle <dir>`:

1. Take `pg_advisory_lock` on a fixed key, which replaces Neo4j's
   `FullregenLease` node. The migrator takes the same key, so loads and
   migrations exclude each other. A second loader waits or exits.
2. Check `pg_dump` version and free disk (sections 2.5 and 2.8), then dump
   the curation and operations tables.
3. Check the projection manifest: every file's SHA-256, row count and header
   must match; the manifest must name the validated source bundle; the
   bundle's validation report must say `import_ready: true`; the unified CSV
   hash the projection read must equal the bundle manifest's input dataset
   hash; and the legacy master hash must be present. The projection refuses on
   the same conditions (section 4.4); the loader re-checks them.
4. Insert a `dataset_versions` row with `load_status = 'loading'`. While it
   exists, curation writes refuse (section 3.2 rule 10).
5. `COPY` each CSV into an `UNLOGGED` staging table `load_<table>`, outside the
   main transaction.
6. In **one transaction**, in dependency order (traditions, sources,
   narrators, bibliographic works, editions, citations, collections, books,
   chapters, hadiths, translations, lexicon profiles, aliases, teacher links,
   chains, chain mentions, hadith assessments, biographical and temporal
   assertions). Evidence tables come before collections and assessments
   because both hold foreign keys into them. For each table:
   - `insert ... select ... from load_<table> on conflict (id) do update set
     <content columns>, changed_in_dataset_version_id = $new, updated_at =
     now(), retired_at = null, retired_in_dataset_version_id = null where
     (<content columns>, t.retired_at) is distinct from (<excluded columns>,
     null)`. Unchanged rows are not touched at all: no new tuple, no WAL, no
     index entries;
   - retire by anti-join: `update <table> t set retired_at = now(),
     retired_in_dataset_version_id = $new where t.retired_at is null and not
     exists (select 1 from load_<table> s where s.id = t.id)`.
   There is no "last seen" column; a row's presence in staging is the fact.
7. Still in the transaction, with an `is distinct from` guard on every
   update: write automatic resolutions from staging; replay live human
   decisions onto `chain_mentions` (only `narrator_surface_decisions` rows
   with `retired_at is null`, matched on the unit key of the decision's
   scope, section 5.5); recompute the derived columns (section 11.2); refresh
   `narrator_transmissions`; and count orphaned decisions (live decisions
   that match no live mention) into `dataset_versions.counts`.
8. Run the invariant checks in section 11.4. If any fails, roll back; the
   database is exactly as it was.
9. Mark the new version `load_status = 'complete'`, `is_current = true`, and the
   previous one `is_current = false`, then commit. `is_current` means "this
   version's content is live". Whether the public may see it is a separate
   rule (section 11.3): only a `release` version, or a non-release version
   with a recorded owner override.
10. Drop the staging tables, release the lock, and run `vacuum (analyze)` on
    the changed pipeline tables.

`hadiths`, `chains` and `chain_mentions` use `fillfactor = 90`, so updates to
derived columns stay HOT and do not touch unrelated indexes.

Readers see either the old data or the new data, never a mixture. Nothing is
deleted by a load. A curated row that points at a retired pipeline row keeps
working; `db:verify` lists such rows, and curated rows whose bound Arabic hash
no longer matches (section 11.4), so a curator can re-point or re-review them.

### 4.4 Producing the load files

The existing Python exporter (`export_bundle.py`, 1,848 lines) and validator
(`validate_bundle.py`, 2,977 lines) stay untouched. A new
`datasets/hadith-data/neo4j_export/export_postgres.py` (estimated 300 to 400
lines, standard library only) reads a **validated** bundle, checks its manifest
hashes, joins the one-to-one relationship files into foreign-key columns and
writes one CSV per pipeline table plus its own manifest bound to the source
bundle's `content_sha256`. It reuses the SQLite staging, sort-key ordering and
`graph_content_hash` machinery so its output is byte-for-byte deterministic.

It refuses to run unless the bundle's validation report says `import_ready:
true` and the SHA-256 of the unified CSV it reads equals the input dataset
hash in the bundle manifest. Its manifest records the unified CSV, rawi file,
legacy master and curation manifest hashes and the extractor version, which
the loader copies to `dataset_versions`.

It writes two streams with separate manifests: `canonical/` (pipeline tables)
and `candidates/` (`translation_candidates`, and `resolution_review_units`
once job J3 output exists). The bundle contract rejects candidate assets as
canonical inputs; the candidate stream keeps them out of every canonical
table instead of re-admitting them under a flag.

What the projection must add, because the Neo4j bundle does not carry it:

| Missing from the bundle | Projection reads it from | Goes to |
| --- | --- | --- |
| Grades: `grade_value` (29,915 rows), `gradings_full` (14,902), `grade_tradition` (31,652), `grade_source` | The 37-column unified CSV | `hadith_assessments` |
| `matn_en` (27,871 rows) | The unified CSV | `translations.matn_text` |
| `school`, `chain_type`, `narration_level`, `category`, `hadith_id`, `volume`, `chapter`, `chapter_no`, `source_display_label` as written | The unified CSV | `hadiths` |
| Collection display order | The source work registry order | `collections.sort_key`, copied to `hadiths.collection_sort_key` |
| English for the 31,652 machine-candidate rows the bundle omits on purpose (29,915 of them have no model identity) | The unified CSV, written to the `candidates/` stream | `translation_candidates`, never public, never searched (section 11) |
| Per-link exact resolution. The bundle resolves a mention only when the whole row resolves (196 links) | Re-run the existing exact resolver (`build_narrator_index`, `resolve_narrator`) per mention | `chain_mentions.narrator_id` with `resolution = 'exact_registry'` and `resolution_basis = 'mention_exact'`, or `'report_atomic'` where the bundle resolved the whole report. Whether mention-exact links count as transmissions is owner question 11 |
| Legacy `chain_indx` (61,938 rows in the committed 26-column master) | The legacy master. It has no `record_id`; each legacy row joins to a hadith only by a **unique** match on (canonical source, SHA-256 of the exact Arabic text), plus the provider hadith id where both sides have one. whitespace in translation text; write blanks as unquoted empty cells, which
`COPY ... (format csv)` loads as NULL; drop `:LABEL`, `:TYPE` and the
duplicated `import_id`. Arabic text is never trimmed or rewritten, and
`arabic_sha256` is always written (the SHA-256 of the empty string for the 8
rows with no Arabic), so section 11.4 can recompute it inside the database.

The 37-column input lives only in the gitignored `datasets/hadith-data/development/`
folder, and the bundle is 646 MB, so production loads always run from the
operator's machine through `DATABASE_PUBLIC_URL`, with Public Access turned on
for the load window only. Inbound load data is not egress; dumps and verify
reads over the TCP proxy are billed as egress.

## 5. Schema

### 5.1 Conventions

- Types: `text` everywhere for strings (no `varchar(n)`), `integer` for years
  and counts, `boolean`, `timestamptz`, `double precision` for coordinates,
  `real` for confidences, `jsonb` only where the content is verbatim or
  variable, `text[]` for short lists.
- "FK" means a foreign key with `on delete restrict` unless stated. Postgres
  does not index foreign keys automatically; section 7.1 lists the indexes.
- **Pipeline bookkeeping columns**, on every pipeline table and not repeated
  below:

  | Column | Type | Null | Meaning |

  never-delete rule. The `curation_audit` row records the change.

**`narrator_transmissions`** (derived materialized view): who narrated from
whom, using only consecutive verified links. If a chain reads A, unknown, C,
no A-to-C link exists. A pair counts only when both links are trustworthy as
adjacency evidence: both mentions inside a chain the bundle resolved
atomically (`chains.resolved`, which kept the branch-shape cross-check), or
both resolved by a human decision. Mention-exact links render on the chain
page but do not create transmissions unless the owner accepts them (section
14 question 11); then `'mention_exact'` joins the basis list below.

```sql
create materialized view narrator_transmissions as
with pairs as (
  select a.narrator_id as student_id, b.narrator_id as teacher_id,
         a.hadith_id, a.position as student_pos, b.position as teacher_pos,
         least(a.confidence, b.confidence) as confidence,
         a.extraction_method
  from chain_mentions a
  join chain_mentions b on b.chain_id = a.chain_id and b.position = a.position + 1
  join chains c on c.id = a.chain_id
  where a.retired_at is null and b.retired_at is null and c.retired_at is null
    and a.narrator_id is not null and b.narrator_id is not null
    and a.resolution in ('exact_registry','human_verified','derived_relation_verified')
    and b.resolution in ('exact_registry','human_verified','derived_relation_verified')
    and ((c.resolved and a.resolution_basis = 'report_atomic' and b.resolution_basis = 'report_atomic')
      or (a.resolution_basis = 'human_decision' and b.resolution_basis = 'human_decision'))
)
select p.student_id, p.teacher_id,
       count(distinct p.hadith_id)::int                                    as hadith_count,
       -- one occurrence per report position pair, not per taḥwīl or co-transmitter branch
       count(distinct (p.hadith_id, p.student_pos, p.teacher_pos))::int    as occurrence_count,
       max(p.confidence)                                                   as confidence,
       array_agg(distinct coalesce(p.extraction_method, 'unspecified'))   as extraction_methods,
       -- guardrail G-6, same rule as temporal-plausibility.ts lines 63 to 111, on ranges
       case
         when sl.birth_min > tl.death_max                                  then 'impossible'
         when sl.disputed or tl.disputed                                   then 'disputed'
         when sl.birth_max is not null and tl.death_min is not null
          and sl.birth_max <= tl.death_min                                 then 'plausible'
         else 'unknown'
       end                                                                 as temporal_plausibility,
       case
         when sl.birth_min > tl.death_max then 'student born after teacher died, on the most permissive bounds'
         when sl.disputed or tl.disputed  then 'verified lifespan claims conflict'
         else null
       end                                                                 as temporal_reason
from pairs p
left join narrator_lifespans sl on sl.narrator_id = p.student_id
left join narrator_lifespans tl on tl.narrator_id = p.teacher_id
group by p.student_id, p.teacher_id,
         sl.birth_min, sl.birth_max, sl.disputed, tl.death_min, tl.death_max, tl.disputed;
```

`source_index` is added to the resolution lists only if the owner approves it
(section 14, question 1). The view has a unique index on (`student_id`,
`teacher_id`) so it can be refreshed concurrently. The TypeScript
`assessTemporalPlausibility` stays as a pure function with a table-driven test
that asserts it agrees with this SQL. Because lifespans come mostly from the
lexicon, the flag inherits the lexicon's unverified status and is labelled so.
Rows with `analytics_excluded` decisions are kept in the view and filtered out
of offline analytics exports.

### 7.2 Arabic search

- At load, the projection computes `text_ar_normalized` and
  `name_ar_normalized` with the project's Arabic `norm()` (diacritics removed,
  alef and ya forms folded). Postgres `unaccent` does not reliably strip
  harakat, so it is not used for Arabic.
- At query time, the search term passes through the TypeScript `norm()`, which
  is byte-equivalent to the Python one under the existing parity test (the
  test stays and moves next to `src/lib/attribution/`). JavaScript `\b` is
  ASCII-only, so word boundaries use `(?![ء-ي])` as that code already does.
- Matching is `text_ar_normalized ilike '%' || $term || '%'` with LIKE
  wildcards escaped, served by the trigram index. Trigram matching was chosen
  over a word-level `tsvector` because Arabic attaches particles to words
  (`بالله`, `وقال`): a whole-word index would miss `الله` inside `بالله`.
- A term must have at least 3 normalized characters. Shorter patterns yield
  no usable trigrams and would recheck every row.
- Results use the single ordering contract of section 7.3, not similarity.

### 7.3 English and name search

- English hadith text, page search: `text_tsv @@ websearch_to_tsquery('english',
  $term)` against `public_translations`. A `tsvector` index is much smaller
  than a trigram index over about 57 MB of English text, which matters under
  the memory priority. This replaces today's substring `CONTAINS`, so a search
  for part of a word no longer matches on the search page; that behaviour
  change is accepted. There is no `ts_rank` ordering.
- English hadith text, typeahead callers (`admin/commentaries/client.tsx:72-74`,
  `admin/comparative/client.tsx:309-312`): a prefix query, `to_tsquery('english',
  <last word> || ':*')` combined with the earlier words, so `fast` finds
  `fasting`.
- Chapter titles, categories and narrator English names: `ilike` against the
  folded columns with trigram indexes, so substring search still works on
  short fields. `name_en_folded` uses `unaccent` so `ʿAbd` matches `Abd`.
- **Query shape.** `searchHadiths` matches three predicates on two tables
  (title, category, English). Postgres cannot combine indexes across tables
  in one `OR`, so the query is a `union` of three index-driven ID sets
  (trigram on `chapter_title_folded`, trigram on `category_folded`, `tsvector`
  on `public_translations`), then one join to `public_hadiths` for filters and
  ordering. Arabic search is a fourth branch when the term contains Arabic.
- **One ordering contract** for every hadith list and search:
  `collection_sort_key, hadith_no_int nulls last, id`. Public pages use
  `limit`/`offset` up to page 200; admin browsing and exports use keyset
  pagination on the same three columns.
- **Counts are capped.** A search counts up to 1,001 matches and shows
  "1,000+" beyond that, so a common term such as `الله` does not recheck the
  whole table for a total on every page view.
- **Abuse limits.** The `app_rw` role has `statement_timeout = 3s`
  (section 2.9). `src/proxy.ts` rate-limits search routes and read actions per
  IP (assumption: 30 requests a minute, in memory, per instance).
- Source and tradition filters resolve aliases in TypeScript before any SQL
  (section 3.2 rule 8). `getTraditionFilterValues` becomes
  `resolveTraditionCode`: `Imami`, `Shia Imami` and `Shia` give `Imami`;
  `Zaydi` and `Shia Zaydi` give `Zaydi`; anything else gives no code and an
  empty result. The SQL compares one enum value, `traditions.code = $code`,
  so a legacy or bookmarked value never reaches an enum cast. Source filters
  compare `collections.name = any($names)` (text), and the ambiguous legacy
  options `Al-Amālī` and `Kitāb al-Ghayba` compare
  `hadiths.source_display_label`, so those rows stay findable without being
  assigned to a compiler.
- Every search is paginated with a capped count. The 50-row cap on filtered
  narrator search and its fake pagination go away.

### 7.4 Vector table design

| Decision | Choice |
| --- | --- |
| Type | `halfvec(N)`, `STORAGE PLAIN` (set by a custom SQL migration; Drizzle has no option for it). `halfvec(1024)` is just over the TOAST threshold, which is why plain storage matters |
| Index | None at launch. pgvector's default exact search has perfect recall and needs no extra memory |
| If N = 1,024 (BGE-M3, the model the project's earlier OCR and search research pointed to) | Also store `embedding_bits bit(1024)`. Query: exact Hamming scan over the bits (about 18 MB) filtered on the table's own `tradition_id`, `is_public` and `retired_at` columns, take the top 200, re-rank those by cosine distance on `halfvec`, then join `hadiths` for the top k only. Hot set about 20 MB; estimated 10 to 50 ms |
| If N = 384 | Exact cosine scan over `halfvec(384)`, about 81 MB; estimated 50 to 200 ms warm |
| Storage on disk | `halfvec(1024)` about 271 MB plus `bit(1024)` about 18 MB; `halfvec(384)` about 81 MB |
| Drizzle support | `halfvec`, `bit`, `cosineDistance`, `hammingDistance` exist in 0.45.4. `create extension vector` is a custom migration in the core stream |
| Memory consequence | Exact scan reads only what it scans, so the 1,024 path keeps about 20 MB hot. An HNSW index at 1,024 dimensions would need about 250 to 350 MB kept in cache, which breaks the budget; that is the flip condition in section 1.3 |

All latency figures are estimates; nothing was measured. Before semantic
search ships, load 99k random vectors into the local `pgvector/pgvector:pg18`
container capped at 256 MB and time both paths cold and warm, with the
filtered query (tradition, `is_public`, `retired_at`), not only `order by ...
limit`.

Free-text semantic search also needs the user's query embedded at request
time, and a 1,024-dimension model cannot run inside a 250 MB app. The first
semantic feature is therefore "similar hadiths", which compares stored vectors
only and needs no model at runtime. Free-text semantic search waits for an
owner decision on a query embedder (section 14, question 8).

## 11. Per-row publication status

The current release gate is all or nothing: a load is publishable only if
every row passes every check, and one unresolved name empties a whole chain.
Under it, 0 of 99,283 rows can publish, and even 19,000 human identity
decisions would reach at most 31,397 complete rows. The gate is right about
what it refuses to do (invent identity, show partial chains as complete, treat
a non-blank cell as reviewed). It is wrong to make completeness a precondition
for showing correct Arabic text.

The new rule: **a row is publishable when every assertion it displays is
verified.** Completeness becomes a tracked number, not a gate. The checks that
define "verified" are not loosened by this design: English stays limited to
`human_verified` and `source_verified` with `quality_status = 'complete'`, as
the data contract says. Two things can widen what is public, and both are
explicit, recorded owner decisions stored as data, never code defaults: a
per-work `collection_rights.english_policy = 'source_provided_allowed'`
(question 5), and `public_override_by` on a non-release dataset version
(question 13).

### 11.1 Facets

| Facet | Where | States, best to worst | What the public sees |
| --- | --- | --- | --- |
| Dataset version | `dataset_versions` | `release`, or `non_release` with `public_override_by`, then `non_release` | Public views serve rows only while the current version is release-class or carries a recorded owner override. Otherwise only reviewer mode sees data |
| Source text | `hadiths.source_text_status` | `present_locator_bound`, `present`, `missing` | `missing` rows are not published |
| Rights | `collection_rights.rights_status` | `cleared`, `pending`, `restricted` (no row means `pending`) | Only `cleared` works publish text or English. This is the one corpus-level gate kept |
| Translation | `translations.state` and `quality_status` | `human_verified`, `source_verified`, `source_provided`; candidates live in `translation_candidates` | English shown, with attribution, when `quality_status = 'complete'`, `arabic_sha256` matches the hadith, and the state is `human_verified` or `source_verified` (or `source_provided` where the work's `english_policy` allows it). Candidates only in reviewer mode |
| Chain | `hadiths.chain_status` | `complete`, `partial`, `unresolved`, `absent_in_source`, `extraction_failed` | The isnad is always shown as written in Arabic; links are overlaid only where verified |
| Link | `chain_mentions.resolution` | `exact_registry`, `human_verified`, `derived_relation_verified` (plus `source_index` if approved), then `undecidable`, `unresolved` | Only the verified ones render as narrator links. Others show the surface verbatim with a neutral "not identified" marker. A candidate name is never shown |
| Grading | `hadiths.grading_status` | `cited_assessments`, `compiler_criterion`, `none_recorded` | Placeholders do not exist; `collection_label` rows are never shown as grades |

### 11.2 How the stored facets are computed

`refresh_publication_facets(hadith_ids)` is a SQL function. The loader calls it
for every hadith after decision replay; `apply_decision` and
`recordChainAbsence` call it for the hadiths they touch. Every update is
guarded with `is distinct from`, so unchanged rows are not rewritten.

| Facet | Rule |
| --- | --- |
| `source_text_status` | `missing` when `text_ar` is null or blank. `present_locator_bound` when the Arabic is hash-bound to an upstream locator (`arabic_sha256`, `source_record_id`, and `url` or `page_ref` all present). This says the text can be traced to its source page; it is not a reviewed identity, so it is not called "verified". Otherwise `present` |
| `chain_status` | No chain rows: `absent_in_source` if a `chain_absence_dispositions` row covers the hadith or its collection, else `extraction_failed`. With chains: `complete` when every mention of every branch is a verified link, `unresolved` when none is, `partial` otherwise |
| `grading_status` | `cited_assessments` when any `cited_ruling` or `compiler_statement` row exists; `compiler_criterion` when only `compiler_criterion` rows exist; else `none_recorded` |
| `chains.verified_link_count` | Count of verified mentions per branch |

### 11.4 What a load must still prove (the kept gates)

`src/db/load/verify.ts` runs these inside the load transaction and fails the
load if any is false. `npm run db:verify` runs the same checks on demand.

| Check | Origin |
| --- | --- |
| Exactly one current dataset version; it carries the attribution disclaimer | Section 9b checks, G-3 |
| A non-release current version is publicly servable only with `public_override_by` set; `curation_manifest_sha256` is present on a `development_nonrelease` version | Release-class activation rule (DV contract) |
| At least 50,000 live hadiths; at least one live narrator | Section 9b checks |
| Every live hadith's `tradition_id` equals its collection's | Source-tradition rule |
| Arabic round trip: for every live hadith, `encode(sha256(convert_to(coalesce(text_ar,''),'UTF8')),'hex') = arabic_sha256` | Bundle `arabic_round_trip` gate, recomputed inside Postgres |
| Retirement is exact: per pipeline table, rows retired by this load equal IDs live before the load minus IDs in staging | Anti-join merge correctness |
| No `chain_mentions` row has a `narrator_id` with a non-rendering resolution, except `source_index` when not approved; every resolved mention has a non-null `confidence` | G-5, "no unverified link rendered as a link"; G-2 |
| No live `narrator_surface_decisions` row lacks a reviewer and time; no `derived_relation` decision has the coarse scope | G-5; derived identity depends on the student |
| Contiguous positions in every chain: positions 0 to `length - 1` | Bundle chain-integrity gate |
| No row in `public_translations` has `quality_status <> 'complete'`, a hash that differs from its hadith's, or a state outside the policy | Translation release gate |
| No `cross_parallels` row's `source_translation_id` points outside `translations`, and no `parallel_research_runs` row points at a candidate | Candidate isolation |
| No `hadith_assessments` row with a placeholder grade | No placeholders |
| No published narrator verdict, bio or event whose citation is missing, retired or unreviewed | Check constraints plus section 5.8; verified again |
| No published event that fails the gate | Enforced by check constraint; verified again |
| Every `narrator_transmissions` row has a `temporal_plausibility` value, a non-null `confidence` and non-empty `extraction_methods` | G-4, G-6 |
| Orphaned decisions, mentions whose surface changed under an unchanged ID, curated rows whose `bound_arabic_sha256` no longer matches, and curated rows pointing at retired pipeline rows are counted in `dataset_versions.counts` and listed by `db:verify` (reported, not fatal) | Curation drift |
| Facet counts recorded in `dataset_versions.counts` | Completeness becomes a KPI |

`db:verify` also checks the server settings (`max_connections = 20`,
`shared_buffers = 64MB`) and that `app_rw` is not a superuser.

The Python side keeps everything it has: fail-closed regeneration, hash
binding, override hash checks, the 12 bundle gates and
`--allow-incomplete-curation` isolation. The publishable-row definition moves
from "complete" to "every shown assertion verified"; the per-mention exact
resolution of section 4.4 is a second, separate change, which is why
mention-exact links do not feed transmissions without owner approval
(question 11).
