# Data architecture and schema

Status: **proposed** (2026-11-21). Replaces Neo4j as the application store.
Nothing in this document is implemented yet.

## Decision

| Concern | Choice |
| --- | --- |
| Store | PostgreSQL (one small instance, tuned for low memory) |
| Access layer | Drizzle ORM; SQL lives in `src/db/queries/`, never in server actions |
| Migrations | `drizzle-kit`, checked in under `drizzle/` |
| Vector search | `pgvector`, in a separate table so it costs nothing until used |
| Text search | `pg_trgm` on normalized Arabic, `tsvector` on English |
| Graph analytics | Offline in Python, results written back as plain columns |
| Bulk load | Python bundle exporter writes CSV, loaded with `COPY` |

### Why not Neo4j

The application never uses a graph feature. Its roughly 100 query call sites
contain no variable-length path, `shortestPath`, APOC, GDS, full-text or vector
index call. Every query is a fixed-depth join such as
`Hadith -> Chain -> Narrator`. Neo4j averaged 1.78 GB of memory over the week
before this was written, and its wake-from-sleep window causes HTTP 500s.

### Why Postgres rather than SQLite

SQLite uses the least memory because it has no server. Postgres is chosen
anyway, for three reasons:

1. The app writes. Commentaries, historical events, locations, comparative
   parallels and motif tags are created through admin actions today, and the
   product direction is shared curation by several people.
2. The same engine already runs locally, so development and production match.
3. `pgvector` is mature; the SQLite equivalent is not yet at 1.0.

Drizzle keeps the door open: the query modules are the only code that would
change if the store moved to SQLite later.

### Memory budget

| Process | Expected resident memory |
| --- | --- |
| Next.js standalone server | 150 to 250 MB |
| Postgres, tuned as below | 100 to 150 MB |
| Neo4j today, for comparison | 1,780 MB average |

These are estimates to be confirmed after the first deploy. Postgres settings:
`shared_buffers=64MB`, `work_mem=4MB`, `maintenance_work_mem=64MB`,
`max_connections=20`. The app uses one pool of at most five connections.

Embeddings are the one thing that can break this budget. 99,283 vectors at
1,024 dimensions are about 400 MB as `vector`, or 200 MB as `halfvec`, and an
HNSW index wants to sit in memory. Use `halfvec`, keep embeddings in their own
table, and do not build the index until semantic search ships.

## Layers

```
datasets/ (Python)            src/db/                    src/app/
  extract, resolve, curate      schema/*.ts   <- DDL       actions/*.ts
  export bundle (CSV)           client.ts                    call queries only
  load with COPY  ------------> queries/*.ts  <----------  pages and components
```

- **`src/db/schema/`** is the single source of truth for table definitions.
  The Python loader checks its CSV headers against the live columns and fails
  on any mismatch.
- **`src/db/queries/`** has one module per area: `hadith`, `narrator`, `isnad`,
  `history`, `commentary`, `comparative`. Each exports typed functions.
- **Server actions** validate input, call a query function and return plain
  objects. They contain no SQL.

## Table ownership

Every table belongs to exactly one writer. This is the rule that keeps a data
reload from destroying curation work.

| Owner | Written by | On reload |
| --- | --- | --- |
| Pipeline | Python bundle loader only | Upserted by stable ID; rows missing from the new bundle get `retired_at` set, never deleted |
| Curation | The app, through server actions | Untouched |

Curation rows point at pipeline rows by stable ID (`hadiths.id`,
`narrators.id`). Those IDs come from immutable upstream keys, so they survive
every rebuild.

## Identifiers

All primary keys are text and namespaced, exactly as the bundle contract
already produces them:

| Entity | Format |
| --- | --- |
| Hadith | `hadith:<record_id>` |
| Narrator | `narrator:rawi:<scholar_indx>` |
| Chain | hadith record plus zero-padded branch number |
| Mention | chain plus zero-padded position |
| Tradition | `tradition:<lowercase name>` |

Curation tables use UUID primary keys generated by the database.

## Schema

Columns common to every pipeline table are omitted below: `provenance text`,
`dataset_version_id` and `retired_at timestamptz`.

### Narrators (pipeline)

| Table | Key columns | Notes |

### Isnad (pipeline)

| Table | Key columns | Notes |
| --- | --- | --- |
| `chains` | `id`, `hadith_id`, `branch`, `length`, `resolved`, `extraction_method`, `sanad_confidence` | One row per branch of a report |
| `chain_mentions` | `id`, `chain_id`, `position`, `surface`, `normalized_surface`, `narrator_id` nullable | Unique on (`chain_id`, `position`) |

`chain_mentions` replaces four graph relationships at once. The name as written
in the source is the row; its place in the chain is `position`; the next link
is simply `position + 1`; and the resolved person is `narrator_id`, left null
when unresolved. `narrator_id` is filled only when every mention in the report
resolves, which preserves the existing all-or-nothing rule and is recorded on
`chains.resolved`.

Who-narrated-from-whom is derived, not stored:

```sql
create materialized view narrator_transmissions as
select a.narrator_id as student_id,
       b.narrator_id as teacher_id,
       count(distinct c.hadith_id) as hadith_count
from chain_mentions a
join chain_mentions b on b.chain_id = a.chain_id and b.position = a.position + 1
join chains c on c.id = a.chain_id
where a.narrator_id is not null and b.narrator_id is not null
group by 1, 2;
```

It is refreshed at the end of each load and serves the narrator network page.

### Assessments (pipeline)

| Table | Key columns | Notes |
| --- | --- | --- |
| `hadith_assessments` | `id`, `hadith_id`, `tradition_id`, `grade_scheme`, `grade`, `grade_source` | A grade always belongs to a tradition's scheme |
| `narrator_assessments` | `id`, `narrator_id`, `tradition_id`, `grade_scheme`, `grade`, `grade_source` | Same shape; never a single reliability value on the narrator |

"No extant evaluation" is represented by the absence of a row. The current
graph stores 352,315 placeholder nodes for it, 88% of all assessments.

The split into two tables is assumed from the current model and must be
checked against the regeneration loader before the first migration.

### Evidence and citations (pipeline, reserved)

Created empty. They are filled only by the citation-curation workflow.

| Table | Purpose |
| --- | --- |
| `bibliographic_works`, `editions` | The printed or digital work a claim cites |
| `citations` | `edition_id`, `locator`, `url`, `review_state` |
| `biographical_assertions` | `narrator_id`, `predicate`, value or year range, `calendar`, `precision`, `review_status`, `citation_id`, `superseded_by` |
| `temporal_assertions` | Same idea for events and epochs |

Competing claims are separate rows. Nothing collapses them into one date.

## How graph questions are answered

| Question | Mechanism |
| --- | --- |
| Chain for one hadith | Join `chains` to `chain_mentions`, ordered by branch and position |
| A narrator's teachers and students | `narrator_transmissions` |
| Hadiths passing through a narrator | `chain_mentions` filtered by `narrator_id` |
| Events during a narrator's lifetime | Interval overlap on Hijri bounds, computed at read time |
| Multi-hop paths (future) | Recursive query over `narrator_transmissions` |
| Centrality, communities (future) | Python over an export of `narrator_transmissions`; 24k nodes and 80k edges fit in memory on a laptop |

## Indexes

- Foreign keys on every `*_id` column used in a join.
- `hadiths (collection_id, hadith_no)` for browsing.
- `chain_mentions (narrator_id)` and the unique `(chain_id, position)`.
- `chain_mentions (normalized_surface)` for resolution work.
- Trigram index on `hadiths.text_ar_normalized` and on narrator names.
- `historical_events (start_year_hijri, end_year_hijri)`.

## Migration order

1. Commit the current working tree and tag it, so everything removed later is
   recoverable from git.
2. Add Drizzle, the schema files and the first migration. Run it against the
   local Postgres.
3. Retarget the bundle exporter from Neo4j import headers to plain CSV headers
   matching the tables, and write the `COPY` loader.
4. Port the query modules one area at a time, then switch the server actions.
5. Export the curation data that exists only in production Neo4j and load it
   into the curation tables.
6. Deploy Postgres on Railway, load, verify, and point the app at it.
7. Take a final dump of the Neo4j volume, then remove the service.

## What gets removed

Only after step 1, and for the Railway items only after step 7.

| Item | Location |
| --- | --- |
| Neo4j client, helpers, schema initializer, seed | `src/lib/db/` |
| Cypher commit path for parallels | `src/lib/comparative/neo4j-commit.ts` |
| Regeneration loaders and their tests | `src/scripts/lib/regen/`, `src/scripts/regen-isnad-graph.ts`, `src/scripts/__tests__/` |
| Archived scripts | `src/scripts/archive/` |
| Neo4j bench, diagnose, drain, verify and backup scripts | `src/scripts/` |
| `neo4j-driver` dependency and the `db:*` scripts that call it | `package.json` |
| Neo4j variables on the app service | Railway |
| Neo4j service and volume | Railway |

Dataset files under `datasets/` are not removed. They are the source of truth
for every rebuild.
