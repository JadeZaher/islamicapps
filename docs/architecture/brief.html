Graph features the app actually uses

The app's queries contain no variable-length paths, shortest-path calls, graph algorithms, or Neo4j search indexes. Every one is a fixed join such as hadith → chain → narrator, which a relational database does with less memory.

How it fits together

datasets/  (Python)              src/db/                        src/app/
  extract chains, resolve names     schema/    table definitions    actions/   validate, then
  curation gates                    client.ts  one small pool         call a query function
  export bundle as CSV              queries/   all SQL lives here   pages and components
  load with COPY  ───────────────►  load/      merge by stable id   ◄────────────────────

One writer per table. Tables are either filled by the Python pipeline or edited through the app, never both. A data reload updates pipeline rows by their permanent ID and leaves curation rows alone, so re-importing the corpus cannot erase commentaries, parallels, or review decisions.

Permanent IDs. A hadith is hadith:<record_id> and a narrator is narrator:rawi:<number>, both derived from keys in the source data. They do not change between rebuilds, which is what lets curation rows point at them safely.

Names are stored as written. Each name in a chain is a row holding the Arabic text as it appears. It links to a narrator identity only when that identity is established. An unresolved name is shown as text, never guessed.

Grades belong to a tradition. A grade is always recorded under the tradition and grading scheme that issued it. There is no single reliability value on a narrator. "No evaluation exists" is the absence of a row, which removes 352,315 placeholder records.

Data gaps

From the July audit of the 99,283-record corpus. Diagnostic jobs that rank these and build review queues are running now; they write new files only.

Narrator names not matched to an identity387,359 of 437,476 name occurrencesThe largest gap. Rank the distinct unmatched names by frequency, propose candidates with evidence, and review the most frequent first.
Reports with a fully resolved chain204 of 99,283Follows from the gap above. Chains are extracted for 84,781 reports; it is the identities that are missing.

Grades for Ibadi and Zaydi reportsnoneSource grading works for those traditions must be acquired.
Cited scholarly claims0The citation tables exist so that biography and history can be entered with a source and page.

The release gate is all-or-nothing today. A load is allowed only when every one of the 99,283 reports has a resolved chain and a human-verified translation, so nothing can be published. The design replaces this with a status on each report, shown honestly to the reader: Arabic present, translation state, chain resolved or shown as written, graded or not.

Order of work

  1. Done. Working tree checkpointed on branch refactor/postgres-drizzle.
  2. Containment. The AI research endpoint can be called by anyone and spends a paid API key. Remove or rotate that key first.
  3. Access control. Admin pages and every write action currently have no sign-in. Add a gate and named curators.
  4. In progress. Build fix. The current code does not compile (39 type errors), which is why the August deploy failed.
  5. In progress. Database foundation. Drizzle schema, client, and migrations applied to the Railway database.
  6. Loader. Project the Python bundle to plain CSV and load it with COPY.
  7. Query port. Rewrite the server actions against Drizzle query modules, one area at a time.
  8. Export curation from Neo4j, read-only: commentaries, events, parallels, tags, and the hand-written narrator biographies.
  9. Cut over on Railway, measure memory, observe for a week.
  10. Retire Neo4j and remove its code, after a final dump and your approval.
  11. Vectors, once an embedding model is chosen.

In progress alongside: five interface lanes (shell and error states, hadith page, narrator page, admin lists, comparative), the conductor reset, and the data-gap diagnostics.
